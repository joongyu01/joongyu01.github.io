02 / 역할 구분
보여 주기, 판단하기, 기억하기
프론트엔드 · FRONTEND
사용자가 만지는 화면
버튼, 입력창, 목록을 보여 주고 사용자 행동을 처리합니다. 웹에서는 주로 HTML·CSS·JavaScript로 만듭니다.
예약 날짜를 고르고, 처리 결과에 따라 ‘예약 완료’를 표시합니다.
백엔드 · BACKEND
서버 쪽의 처리 로직
로그인 여부, 예약 권한, 입력값, 업무 규칙을 확인합니다. 필요한 데이터를 읽거나 저장하고 결과를 돌려줍니다.
“이 직원이 이 회의실을 예약할 수 있는가?”를 검사합니다.
데이터베이스 · DATABASE
함께 쓰는 정보의 저장소
예약, 직원, 회의실 같은 데이터를 구조에 맞춰 보관합니다. DBMS라는 관리 프로그램이 조회·수정 등을 처리합니다.
브라우저를 닫아도 다음 날 예약 기록을 다시 찾을 수 있습니다.
프론트엔드에서 버튼을 숨기는 것만으로는 권한을 막을 수 없습니다. 서버 쪽에서도 권한을 검사해야 합니다. 모든 서비스가 이 그림과 똑같은 구조를 쓰는 것은 아닙니다.
서버는 큰 컴퓨터이고, 클라우드는 인터넷인가요?
서버는 요청에 응답하는 프로그램 또는 그 프로그램이 실행되는 컴퓨터를 뜻합니다. 클라이언트는 요청하는 쪽입니다. 클라우드는 다른 사업자의 컴퓨팅 자원을 네트워크로 이용하는 방식입니다. 인터넷 자체와 같은 말은 아닙니다.


03 / DB 이해
엑셀처럼 생겼지만, 여러 사람이 함께 쓰는 규칙이 있습니다.
엑셀도 자료 정리에 유용합니다. 여러 사용자가 동시에 예약하고 권한별로 조회해야 한다면, DBMS가 일관성과 동시 처리를 관리하도록 설계하는 편이 적합합니다.
파일을 각자 가지고 있다면
직원 A와 B가 같은 시간표를 내려받아 각각 예약합니다. 어느 파일이 최신인지, 누가 먼저 예약했는지 맞추기 어렵습니다.
공통 DB를 사용한다면
같은 저장소의 기록을 확인합니다. 백엔드와 DB의 제약을 함께 설계하면 같은 시간의 중복 예약을 막을 수 있습니다.
DB를 설치했다고 중복 예약이 저절로 사라지지는 않습니다. 검사·저장 과정과 제약 조건을 올바르게 설계해야 합니다. 이 예시는 한 시간 단위 예약을 가정합니다.

employee_id는 직원 테이블을 참조하는 외래 키
기본 키(PK)는 각 행을 고유하게 구분합니다. 외래 키(FK)는 다른 테이블의 키를 참조해 연결합니다. 직원 이름을 매번 복사하는 대신 직원 번호로 연결하면 이름 변경을 한 곳에서 관리할 수 있습니다.
DB와 DBMS는 같은 뜻인가요?
DB는 데이터의 모음이고, DBMS는 그것을 관리하는 소프트웨어입니다. PostgreSQL, MySQL, Oracle Database 등이 DBMS입니다. 현업에서 “DB”라고 줄여 말할 때 두 의미가 섞이기도 합니다. 여기서는 표 구조를 쓰는 관계형 DB를 중심으로 설명합니다. 모든 DB가 표 형태인 것은 아닙니다.


04 / API 이해
API는 프로그램끼리 사용하는 ‘약속된 접점’입니다.
사람은 화면의 버튼을 누릅니다. 프로그램은 API에 정해진 요청을 보냅니다. 어디로, 어떤 형식으로 요청하면 무엇을 돌려주는지 약속합니다. 아래는 웹 API의 예시입니다.
요청 · “이 예약을 만들어 주세요.”
POST /api/reservations
Content-Type: application/json

{
  "room_id": "A",
  "start_time": "2026-11-03T10:00:00+09:00"
}
POST는 생성 등의 처리를 요청하는 HTTP 메서드입니다. 주소와 메서드를 함께 보면 어떤 작업인지 알 수 있습니다. 사용자 식별은 보통 로그인 정보로 확인합니다.
응답 · “예약 104번을 만들었습니다.”
201 Created
Content-Type: application/json

{
  "id": 104,
  "status": "confirmed"
}
201은 생성 성공을 나타내는 상태 코드입니다. JSON은 이름과 값으로 데이터를 표현하는 형식입니다. 화면은 이 결과를 받아 사람에게 보여 줍니다.
API ≠ DB, API ≠ 데이터 파일. API는 접근 방법이고, DB는 저장소입니다. API는 DB 없이 계산만 하거나 다른 서비스에 요청할 수도 있습니다. 모든 API가 웹이나 JSON을 쓰는 것도 아닙니다.
GET · 조회 요청
예약 목록을 가져옵니다.
GET /api/reservations
인증 · 누구인가?
로그인한 사용자가 누구인지 확인합니다. 세션이나 토큰 등을 사용할 수 있습니다.
인가 · 해도 되는가?
그 사용자에게 권한이 있는지 확인합니다. 로그인했다고 모든 예약을 취소할 수 있는 것은 아닙니다.


05 / SQL 체험
쿼리는 데이터에 보내는 질문이나 작업 요청입니다.
SQL은 관계형 DB에서 데이터를 다루는 언어입니다. 여기서는 조회 명령인 SELECT를 체험합니다. 조건을 바꿔 어떤 행이 남는지 보세요.
예약 번호회의실직원 번호
브라우저 안의 가상 데이터를 필터링하는 학습용 모형입니다. 실제 DB에 SQL을 전송하지 않습니다.
SELECT · 무엇을
결과로 받을 컬럼을 고릅니다. 여기서는 예약 번호, 회의실, 직원 번호입니다.
FROM · 어디에서
조회할 테이블을 정합니다. 여기서는 reservations입니다.
WHERE · 어떤 조건
조건에 맞는 행만 남깁니다. ORDER BY는 표시 순서를 지정합니다.
조회 말고 추가·수정·삭제도 쿼리인가요?
현업에서는 SQL 작업 전반을 쿼리라고 부르기도 합니다. INSERT는 추가, UPDATE는 수정, DELETE는 삭제입니다. 이를 조회(Read)와 함께 CRUD라고 부릅니다. UPDATE·DELETE에서 WHERE가 빠지면 전체 행이 대상이 될 수 있습니다.
JOIN은 무엇인가요?
여러 테이블의 데이터를 조건으로 연결해 조회하는 작업입니다. 예약 테이블의 직원 번호와 직원 테이블의 직원 번호를 연결하면, 예약 목록에 직원 이름도 함께 보여 줄 수 있습니다. 원본 테이블을 하나로 합쳐 저장한다는 뜻은 아닙니다.

07 / 업무에서 활용
“안 돼요”를 구체적인 상황으로 바꿔 말하기
직접 원인을 확정할 필요는 없습니다. 관찰한 증상과 발생 조건을 전달하면 담당자가 확인할 범위를 좁힐 수 있습니다.
관찰한 현상확인할 단서
버튼이 가려져 클릭이 안 됨화면 크기·확대 비율·브라우저·프론트엔드 표시
예약 요청에 403 표시계정의 권한·서버의 접근 정책
409와 함께 “이미 예약됨” 표시이 예시에서는 예약 충돌 · 실제 API 규약 확인
요청 후 500 오류 표시서버 쪽 처리 실패 · 해당 시각의 로그 확인
오래 기다려도 응답이 없음네트워크·서버·DB 지연 등 여러 가능성 확인
오류 번호만으로 정확한 원인을 단정할 수는 없습니다. 발생 시각, 화면 주소, 수행한 작업, 오류 문구, 반복 여부를 함께 전달하세요.
이렇게 전달하면 좋습니다
“오늘 10시 15분, 회의실 예약 화면에서 A회의실 14시를 선택하고 예약을 눌렀습니다. ‘403 권한 없음’이 나왔고 다시 해도 같습니다. 조회는 되지만 예약만 되지 않습니다.”
캡처에는 비밀번호, 인증 토큰, 불필요한 개인정보가 드러나지 않도록 확인합니다.
개발 → 테스트 → 배포 → 운영은 어떻게 다른가요?
개발은 기능을 만드는 과정입니다. 테스트는 기대한 동작과 예외 상황을 확인하는 과정입니다. 배포는 만든 버전을 사용 환경에 반영하는 작업입니다. 운영은 실제 이용 중의 오류·성능·데이터를 관리하는 일입니다. 개발용 데이터와 실제 업무 데이터는 구분해 다룹니다.


08 / 이해 확인
내 말로 설명할 수 있으면 충분합니다.
답을 고르면 이유를 확인할 수 있습니다. 점수나 선택 내용은 서버에 저장하지 않습니다.
동료에게 이 네 문장을 설명해 보세요.
  • 프론트엔드는 사용자의 행동을 받고 결과를 보여 줍니다.
  • API는 프로그램이 기능과 데이터를 요청하는 약속된 접점입니다.
  • 백엔드는 권한과 업무 규칙을 확인하고 처리를 수행합니다.
  • DB는 업무 데이터를 보관하고 조회·변경할 수 있게 합니다.
