1. 가장 먼저 풀 것: 교수자 TCP 예제

출처: TCP connection.pdf 1쪽. 초기 SEQ는 클라이언트 2000, 서버 3000. 연결 후 클라이언트가 200바이트를 보내고 서버도 200바이트를 보낸 뒤 클라이언트가 종료한다.

계산 규칙은 세 가지

• SEQ는 그 세그먼트에 실린 첫 데이터 바이트의 번호다. 양방향은 각각 독립된 번호 공간을 쓴다.

• ACK는 상대방에게서 다음으로 연속 수신하기를 기대하는 바이트 번호다. 마지막으로 받은 바이트 번호가 아니다.

• 데이터 L바이트는 L만큼, SYN·FIN은 각각 1만큼 번호를 소비한다. 데이터 없는 순수 ACK는 번호를 소비하지 않는다.

원본 모범답안 그림을 그대로 계산하면

시험에서 설명할 문장

SYN 교환으로 양쪽 초기 순서번호를 동기화한다. 각 방향의 200바이트 전송 후 다음 순서번호는 각각 2201과 3201이다. FIN도 순서번호 하나를 소비하므로 최종 확인 응답 번호는 2202와 3202가 된다.

원본의 표현 차이까지 알고 가기

문제 문장은 서버가 응답과 함께 데이터를 보낸다고 표현하지만, 모범답안 그림은 서버의 순수 ACK와 DATA를 분리한다. 위 표는 그림을 따른다. ACK와 DATA를 합치면 5·6단계가 하나가 되며 SEQ=3001, ACK=2201, 길이=200이다.

일반 종료는 FIN → ACK → FIN → ACK의 4단계다. 원본 그림은 가운데 ACK와 FIN을 합쳐 3개 세그먼트로 그렸다. 따라서 “TCP 종료 패킷은 무조건 4개”라고 단정하면 안 된다.

2. TCP 숫자 문제를 스스로 푸는 법

출처: 3장 PDF 7~10쪽, TCP connection 보충자료. 아래 숫자 변형은 새로 만든 연습이다.

누적 ACK

SEQ=100, 길이=100인 데이터가 오면 100~199를 받았으므로 ACK=200. 이어서 SEQ=200이 손실되고 SEQ=300, 400, 500이 도착하면 누락 구간 때문에 ACK=200이 반복된다.

수신자가 뒤쪽 데이터를 버퍼링했다면 누락된 200~299가 재전송되어 도착한 뒤 ACK는 600으로 이동한다. 뒤쪽 조각을 받았다고 ACK를 무조건 400, 500으로 올리는 것이 아니다.

직접 계산

• Q1. 초기 번호가 C=1000, S=5000이다. 연결 직후 첫 데이터 SEQ는? → C=1001, S=5001.

• Q2. C가 350바이트를 보냈다. 서버 ACK는? → 1001+350=1351.

• Q3. 서버가 순수 ACK 두 번을 보냈다. 서버 다음 데이터 SEQ는? → 여전히 5001. ACK 수와 무관하다.

• Q4. S가 120바이트를 보냈다. C의 ACK는? → 5001+120=5121.

• Q5. C가 FIN을 보낸다. FIN의 SEQ와 S의 확인 번호는? → FIN SEQ=1351, 확인 ACK=1352.

• Q6. S도 FIN을 보낸다. C의 최종 ACK는? → 5122.

손실과 재전송

빠른 재전송: 전형적으로 동일 ACK의 중복 ACK 3개를 받으면 누락을 추정하고 타임아웃 전 재전송한다. 첫 ACK와 중복 ACK를 구분한다.

타임아웃 재전송: RTO 안에 확인이 없으면 재전송한다. RTO는 RTT 추정에 기반하며 반복 실패하면 대기 시간을 늘리는 백오프를 적용한다. RTT는 왕복 시간, RTO는 재전송을 기다리는 제한 시간이다.

윈도우 계산

송신 윈도우 제한 = min(rwnd, cwnd). rwnd=8000B, cwnd=5000B이면 제한은 5000B. 이미 ACK를 못 받은 데이터가 2000B 있으면 추가 전송 여유는 단순화하여 3000B다.

MSS는 TCP 데이터 부분의 최대 크기다. 헤더를 포함한 전체 세그먼트 크기와 혼동하지 않는다. SACK는 연속되지 않게 받은 블록 정보도 알려 손실 복구를 효율화한다.

손으로 그릴 때

왼쪽 C, 오른쪽 S를 쓰고 시간은 아래로 흐르게 그린다. 화살표마다 종류, SEQ, ACK, 데이터 길이를 적는다. 화살표를 하나 그릴 때마다 해당 송신자의 다음 SEQ만 갱신한다.

영상 계산 연습: 헤더·ACK·윈도·마스크

아래 문제는 영상 설명을 토대로 만든 복습이다. 교수자 원문 시험 문제가 아니다.

1. Data Offset: 단위가 핵심

전송계층2 13:05~15:47. Data Offset 필드는 4비트이며, 값 × 4바이트 = TCP 헤더 길이다. 최소 5 → 20B, 최대 15 → 60B. 옵션과 패딩은 최대 40B.

• 값이 8이면? 헤더 32B, 기본 20B를 빼면 옵션+패딩 12B.

• 옵션이 3B라면? 20+3+패딩 1=24B. Data Offset=6.

• 헤더가 28B라면? 28÷4=7. 28을 그대로 쓰는 것이 아니다.

패딩 설명: 전송계층2 20:23. TCP payload 시작 위치를 알아야 헤더와 데이터를 나눌 수 있다.

2. 누적 ACK: 영상의 손실 예시

전송계층3 07:56~13:38. SEQ 100, 200, 300, 400을 각 100B 받으면 다음 기대 번호는 500이다. 500~599가 빠지고 600~899가 도착해도 ACK는 500이다.

누락된 500~599가 도착하고 뒤 데이터가 버퍼에 있다면 ACK=900. 중간 자막의 말실수보다 뒤에서 정정한 번호와 바이트 계산을 기준으로 정리했다.

3. 슬라이딩 윈도

전송계층3 14:01~16:53. 창 크기 800B, 최초 범위 [0,799]. ACK=500이면 [500,1299]로 이동한다. 1300은 오른쪽 끝 다음 번호다. 창 전체가 확인될 때까지 기다려야 하는 것은 아니다.

Q. rwnd=8000B, cwnd=5000B, 아직 ACK 없는 데이터=2000B라면? 제한 min(8000,5000)=5000B, 새로 보낼 여유 3000B.

4. 같은 네트워크인가?

1장2 06:04~08:30. IP와 마스크를 비트 AND한 네트워크 주소를 비교한다. /24=255.255.255.0.

192.168.1.10/24와 192.168.1.200/24 → 둘 다 192.168.1.0, 같은 망. 192.168.2.10/24 → 다른 망, 보통 게이트웨이로 전달한다.

/24일 때 앞 세 옥텟을 비교하는 간편법을 쓸 수 있다. 모든 마스크에서 앞 세 자리만 비교하는 것은 아니다.

3. 1장: 네트워크의 뼈대

출처: 1장 PDF 1~7쪽. 용어 정의만 외우지 말고 웹 접속 과정에 연결한다.

네트워크·인터넷·웹

네트워크는 장치들이 연결되어 데이터를 교환하는 망이다. 구성 요소는 노드(장치), 링크(통신 경로), 프로토콜(통신 규칙)이다. 인터넷은 서로 연결된 네트워크들의 집합이고, 웹은 인터넷 위에서 동작하는 서비스 중 하나다. 이메일·게임도 인터넷을 쓰지만 전부 웹인 것은 아니다.

패킷은 데이터를 나누어 보내는 전송 단위다. 헤더에는 주소·식별·제어 정보가, 페이로드에는 전달할 데이터가 들어간다. 패킷이라는 말은 문맥에 따라 넓게 쓰며, 정확한 계층별 이름은 따로 구분한다.

영상 연결: 1장1 13:49~17:31 주소 구분, 17:39~20:43 캡슐화. 1장2 07:04 마스크 강조, 20:39 지연 강조.

MAC·IP·포트

구분답하는 질문대표 계층
MAC지금 링크에서 어느 인터페이스로 보낼까?데이터링크
IP어느 네트워크의 어느 장치로 갈까?네트워크
포트그 장치의 어느 통신 끝점·서비스로 보낼까?전송

주소 3개는 경쟁하는 대안이 아니다. 한 통신에서 함께 쓰인다. 같은 서브넷이면 직접 전달하고, 다른 서브넷이면 기본 게이트웨이로 보낸다. 서브넷 마스크로 네트워크 부분을 비교한다.

캡슐화

HTTP 메시지 → TCP 세그먼트 → IP 패킷 → Ethernet 프레임 → 비트/신호. 아래 계층으로 내려가며 필요한 제어 정보를 붙이고, 수신 측은 반대로 제거하면서 위로 전달한다.

라우터를 지날 때 링크의 프레임은 새로 구성된다. IP 목적지는 일반적인 라우팅에서 최종 목적지를 가리키지만, 현재 링크의 목적지 MAC은 다음 홉을 가리킬 수 있다. NAT 같은 주소 변환은 별도 동작이다.

성능을 설명하는 단어

• 대역폭: 링크의 최대 전송 용량. 처리량: 실제로 관측된 전송량. 높은 요금제 속도가 실제 다운로드 속도를 보장하지는 않는다.

• 지연: 데이터가 도착할 때까지 걸리는 시간. 전파·전송·처리·큐잉 지연을 구분한다.

• 지터: 지연의 변동. 평균 지연이 낮아도 들쭉날쭉하면 통화가 끊길 수 있다.

• 손실: 패킷이 목적지에 도달하지 못함. 재전송은 신뢰성을 높이지만 시간이 더 걸린다.

망의 규모와 구성

PAN은 개인 주변, LAN은 건물·조직의 근거리, MAN은 도시 규모, WAN은 광역이다. 종단 시스템은 데이터를 만들고 소비한다. 액세스망은 종단을 코어망에 연결한다. 코어망은 여러 망을 이어 준다.

ISP는 접속 서비스 사업자, AS는 단일 관리·라우팅 정책을 가진 망 집합, IX는 망들이 트래픽을 교환하는 접점이다. AS 간 경로 교환에는 BGP를 쓴다. 정의를 구분하는 수준으로 우선 학습한다.

TCP/IP에 대응시키기

응용 = OSI 5~7, 전송 = OSI 4, 인터넷 = OSI 3, 네트워크 접근 = OSI 1~2. 물리와 링크를 나누어 5계층으로 설명하는 경우도 있다. 수업 보충자료의 스택은 4계층이다.

계층 기능 설명과 특정 프로토콜의 보장을 구분한다. 전송 계층이라고 모두 신뢰적 전송을 하는 것은 아니다. UDP는 TCP의 재전송·순서 보장을 제공하지 않는다. 데이터링크도 모든 기술이 오류 정정·재전송을 제공하는 것은 아니다.

장비 비교

• 리피터·허브: L1. 신호를 재생·전달한다. 전통적인 허브는 주소를 보고 골라 보내지 않는다.

• 브리지·L2 스위치: MAC 주소를 바탕으로 프레임을 전달한다. 송신지 MAC으로 테이블을 학습하고 목적지 MAC으로 전달할 포트를 판단한다.

• 목적지 MAC을 모르면: 들어온 포트를 제외한 같은 브로드캐스트 도메인의 포트로 플러딩한다.

• 라우터·L3 스위치: IP와 라우팅 테이블을 사용한다. 경로가 없으면 기본 경로를 사용하거나 폐기한다. L2의 플러딩과 혼동하지 않는다.

• L4 스위치: 포트 등 전송 정보를 활용한 트래픽 분산. 프록시: 응용 요청을 중계하며 캐싱·보안 기능을 수행할 수 있다.

• 게이트웨이: 문맥을 본다. 보충자료의 프로토콜 변환 게이트웨이와 PC 설정의 기본 게이트웨이(보통 라우터)는 같은 뜻으로만 외우면 안 된다.

Ethernet과 IEEE

802.3 = Ethernet, 802.11 = 무선 LAN, 802.15 = 무선 PAN. MAC 주소는 보통 6바이트. Ethernet 프레임에는 목적지·송신지 MAC, Type/Length, 데이터, FCS가 있다. FCS는 오류 검출에 쓰인다.

CSMA/CD는 공유 매체·반이중 Ethernet의 충돌 감지 방식이다. 현대적인 스위치 기반 전이중 링크에 충돌 감지를 그대로 적용하지 않는다.

보충자료 23쪽의 FastEthernet 1000Mbps 표기는 오기로 판단된다. Fast Ethernet은 100Mbps, Gigabit Ethernet은 1000Mbps다. 이 수치를 그대로 잘못 암기하지 않는다.

5. 2장: HTTP를 읽을 수 있어야 한다

출처: 2장 PDF 2~16쪽. 요청과 응답의 구조, 상태 코드, 버전 차이를 먼저 정리한다.

응용과 소켓

응용 프로그램은 HTTP·DNS 같은 메시지를 만들고 소켓 API로 전송 서비스를 사용한다. IP가 장치를, 포트가 그 장치 안의 통신 끝점을 구분한다. 클라이언트-서버는 서버가 요청에 응답한다. P2P에서는 참여자가 받는 역할과 제공하는 역할을 함께 할 수 있다.

URL과 메시지

https://example.com:443/shop?id=7#review → 스킴 https / 호스트 example.com / 포트 443 / 경로 /shop / 쿼리 id=7 / 프래그먼트 review. 프래그먼트는 일반 HTTP 요청 대상으로 서버에 보내지지 않고 클라이언트가 사용한다.

요청 예: GET /index.html HTTP/1.1. 응답 예: HTTP/1.1 200 OK. HTTP/1.1 메시지는 시작 줄·헤더·빈 줄·선택적인 본문으로 읽는다. HTTP/2·3의 전송 형식까지 텍스트 줄 구조라고 일반화하지 않는다.

메서드와 헤더

• GET: 조회. POST: 제출·처리 요청. PUT: 대상 표현을 대체. PATCH: 부분 수정. DELETE: 삭제 요청.

• Host: 대상 호스트. Content-Type: 본문 형식. Content-Length: 본문 길이. User-Agent: 클라이언트 정보.

• Authorization: 인증 정보. Cookie: 클라이언트가 보내는 쿠키. Set-Cookie: 서버가 쿠키 저장을 지시하는 응답 헤더.

HTTPS

TLS로 기밀성·무결성·인증을 제공한다. 암호화되었다고 판매자가 정직하거나 콘텐츠가 안전하다는 뜻은 아니다. TLS의 서버 인증서 검증과 HTTP 로그인 인증도 별개다.

SNI는 클라이언트가 TLS 연결 시 원하는 서버 이름을 알리는 확장이다. SAN은 인증서가 유효한 이름 목록이다. 요청한 도메인이 SAN에 들어 있는지, 유효기간·신뢰 체인이 맞는지 확인한다.

6. 쿠키·캐시·HTTP/2·HTTP/3

출처: 2장 PDF 8~16쪽, 3장 PDF 13~15쪽.

쿠키와 세션: 상태가 없는 HTTP에서 로그인 유지

HTTP 자체는 이전 요청의 로그인 상태를 자동으로 기억하지 않는다. 서버는 로그인 성공 후 세션 식별자를 발급하고 Set-Cookie로 전달한다. 브라우저는 적용 범위에 맞는 다음 요청에 Cookie를 붙인다. 서버는 식별자로 저장된 세션 상태를 찾는다.

쿠키는 클라이언트에 저장되는 데이터다. 서버 세션은 서버 측 상태다. 둘을 모두 서버에 저장한다고 쓰지 않는다. 실제 서비스는 서버 세션 외에 토큰 방식도 사용할 수 있다.

캐시: 같은 내용을 다시 받지 않기

첫 요청 → 200 OK + 본문 + ETag 저장. 다음 요청에서 If-None-Match로 기존 ETag를 보냄 → 같으면 304, 다르면 200과 새 본문. 304는 오류가 아니며 본문을 다시 받지 않고 기존 캐시를 사용한다.

Cache-Control은 캐시 사용·유효기간 정책을 지정한다. 쿠키는 사용자 상태를 전달하는 수단이고, 캐시는 리소스 재사용이다. 둘의 목적을 구분한다.

버전별 핵심 차이

버전전송 기반핵심
HTTP/1.1TCP텍스트 형식, 연결 재사용 가능
HTTP/2TCP이진 프레임·스트림 다중화·헤더 압축
HTTP/3QUIC, UDP 기반스트림 독립성·TLS 1.3 통합·이동성

HTTP/2는 하나의 TCP 연결에 여러 스트림을 섞어 보낸다. 하지만 TCP는 하나의 순서 있는 바이트 스트림을 전달하므로 앞쪽 손실이 다른 HTTP 스트림까지 지연시킬 수 있다. 이것이 전송 계층의 HOL blocking 문제다.

QUIC은 스트림별로 순서 전달을 관리해 한 스트림의 손실이 다른 스트림의 전달을 불필요하게 막는 문제를 줄인다. 손실이 아예 없어지거나 모든 지연이 사라지는 것은 아니다. 혼잡 제어 등 연결 차원의 영향은 공유할 수 있다.

QUIC에서 반드시 기억할 점

• UDP 위에서 동작하지만 QUIC 자체가 손실 복구, 흐름·혼잡 제어, 신뢰적인 스트림 기능을 구현한다.

• TLS 1.3 핸드셰이크를 통합한다. 일반적인 초기 연결은 1 RTT, 조건이 맞는 재접속에서 0-RTT가 가능하다. 항상 0-RTT라고 쓰지 않는다.

• Connection ID로 연결을 식별하여 Wi-Fi에서 이동통신으로 바뀌는 등 IP·포트 변화 시 연결을 이어갈 수 있다.

• UDP 443이 보이면 QUIC 가능성이 있다. 포트 번호만으로 모든 패킷을 QUIC이라고 확정하지는 않는다.

출처: 2장 PDF 4~5쪽, 17~22쪽. 암기한 포트를 서비스 흐름과 함께 설명한다.

DNS의 역할과 흐름

DNS는 도메인에 관한 정보를 제공하는 분산 이름 시스템이다. 대표적으로 도메인 이름을 IP 주소로 바꾼다. 브라우저가 매번 루트부터 직접 모두 질의한다고 생각하지 않는다.

클라이언트 → 재귀 리졸버 → 루트 → TLD(.com 등) → 권한 DNS. 재귀 리졸버가 중간 서버의 안내를 따라 답을 찾고 클라이언트에 돌려준다. 유효한 캐시가 있으면 일부 단계를 생략한다.

TTL은 DNS 정보의 캐시 유효기간이다. IP 패킷의 TTL과 목적·단위가 다르다. 서버 주소를 바꿔도 기존 TTL 동안 예전 정보가 남을 수 있다. 한 PC의 캐시를 비웠다고 모든 리졸버 캐시가 지워지는 것은 아니다.

DNS는 보통 UDP 53을 쓰지만 TCP 53도 사용한다. “DNS는 무조건 UDP만”은 오답이다.

메일 흐름

보내는 사용자 → SMTP 제출 서버 → SMTP로 수신 서버에 전달 → 수신자가 POP3/IMAP으로 읽기. SMTP는 보내기·서버 간 전달, POP3/IMAP은 수신·조회에 사용한다.

POP3는 내려받아 로컬에서 읽는 방식에 가깝다. IMAP은 서버의 메일함 상태를 여러 기기와 동기화한다. POP3가 언제나 서버 원본을 삭제한다고 단정하지 않는다.

8. 3장: 전송 계층 비교와 제어

출처: 3장 PDF 2~16쪽.

프로세스까지 전달하는 계층

IP는 호스트 사이 전달을 다루고, 전송 계층은 그 안의 응용 프로세스 간 통신을 제공한다. 송신 시 여러 소켓 데이터를 모으는 것이 다중화, 수신 시 적절한 소켓으로 나누는 것이 역다중화다.

소켓 끝점은 IP와 포트로 표현한다. 흐름의 5-튜플은 출발지 IP·출발지 포트·목적지 IP·목적지 포트·전송 프로토콜이다. TCP 연결 식별은 TCP라는 전제하에 네 주소·포트 값으로 설명하기도 한다.

포트는 16비트다. 잘 알려진 포트 0~1023, 등록 포트 1024~49151, 동적·사설 포트 49152~65535. OS의 실제 임시 포트 범위는 설정에 따라 달라질 수 있다.

TCP의 신뢰성이 영구적인 단절에서도 반드시 전달된다는 뜻은 아니다. 재전송으로 복구를 시도하고 실패를 알릴 수 있다. UDP에 신뢰성이 필요하면 상위 프로토콜이 구현할 수 있다.

UDP도 체크섬으로 손상 검출을 할 수 있다. “재전송 없음”과 “오류 검출 없음”은 다르다. 실시간 음성은 늦게 도착한 과거 음성보다 다음 음성이 유용할 수 있어 지연을 우선한다.

영상 연결: 전송계층1 20:13~23:48 끝점·포트·5-튜플. 전송계층3 02:36~03:45 양방향을 각각 닫는 이유. 전송계층4 00:11~04:03 수신자 버퍼와 네트워크 혼잡 구분.

흐름 제어와 혼잡 제어

흐름 제어는 수신자 버퍼가 넘치지 않도록 rwnd로 제한한다. 혼잡 제어는 네트워크를 과부하시키지 않도록 cwnd로 제한한다. 송신 가능 범위는 둘 중 작은 값으로 제한된다.

느린 시작에서는 작은 윈도우에서 시작해 전형적으로 RTT마다 빠르게 증가한다. 혼잡 회피 단계에서는 더 완만하게 늘리고, 손실이 감지되면 줄인다. 구체적 감소 폭은 알고리즘·손실 감지 방식에 따라 달라진다.

TCP 플래그와 상태

SYN 연결 시작, ACK 확인번호 유효, FIN 정상적인 한 방향 종료, RST 즉시 중단·거부, PSH 신속한 상위 전달 요청, URG 긴급 포인터 유효.

LISTEN은 연결 대기, SYN-SENT는 요청 후 응답 대기, ESTABLISHED는 연결 성립이다. 먼저 종료하는 쪽의 TIME-WAIT는 마지막 ACK 손실에 대응하고 오래된 세그먼트가 새 연결에 영향을 주지 않도록 기다리는 상태다.

명령을 목적과 짝지어 외우기

• ipconfig /all: IP·마스크·게이트웨이·DNS·DHCP 설정.

• ping: ICMP 기반 도달성·RTT. 실패했다고 서버 다운을 단정하지 않는다. ICMP 차단 가능성이 있다.

• tracert: 경유 경로와 응답 시간을 관찰. 별표만으로 그 라우터가 고장이라고 확정하지 않는다.

• nslookup: DNS 질의. arp -a: IP-MAC 캐시. route print: 라우팅 테이블.

• netstat -ano: 연결·포트·상태·PID. netstat -s: 프로토콜 통계·TCP 재전송 등.

• Test-NetConnection 대상 -Port 443: TCP 포트 연결 가능 여부. True여도 HTTP 서비스 정상까지 보장하지 않는다.

• curl -I: 응답 헤더. curl -I -L: 리다이렉트를 따라가며 헤더 확인.

Wireshark를 읽는 관점

Wireshark는 실제 패킷을 관찰하고, Packet Tracer는 가상 네트워크를 구성·시뮬레이션한다. 캡처 필터는 무엇을 수집할지, 디스플레이 필터는 수집한 것 중 무엇을 보여줄지 결정한다.

디스플레이 필터 예: dns / icmp / tcp.port == 443 / udp.port == 53 / udp.port == 443. tcp.port == 443은 양쪽 중 어느 포트든 443인 TCP를 고른다.

TCP SYN → SYN+ACK → ACK 순서를 확인한다. 재전송·중복 ACK 증가는 손실 징후지만 캡처 누락·순서 뒤바뀜 등도 점검한다. HTTPS의 암호화된 응용 본문은 키 없이 일반 평문 HTTP처럼 읽을 수 없다.

10. 서술형 예상문제와 답안

교수자 원문 문제가 아니라 확보한 교안에서 새로 만든 복습 문제다. 핵심 단어만 외우지 말고 인과관계를 두세 문장으로 설명한다.

Q1. 브라우저에 HTTPS 주소를 입력한 뒤 페이지가 뜨기까지?

DNS로 서버 주소를 얻고 TCP 또는 QUIC 연결을 준비한다. TLS로 서버를 인증하고 암호화 통신을 준비한 뒤 HTTP 요청을 보낸다. 서버 응답의 HTML을 해석하고 필요한 이미지·스크립트를 추가로 요청한다. 캐시가 있으면 일부 절차·전송이 줄어든다.

Q2. 흐름 제어와 혼잡 제어의 차이는?

흐름 제어는 수신자가 처리할 수 있는 양을 넘어 버퍼가 넘치는 것을 막으며 rwnd를 사용한다. 혼잡 제어는 네트워크의 혼잡을 피하도록 송신량을 조절하며 cwnd를 사용한다. 실제 송신 윈도우는 두 값 중 작은 값의 제한을 받는다.

Q3. UDP 위의 QUIC이 신뢰적인 이유는?

UDP 자체에는 재전송·순서 보장 등이 없지만 QUIC이 그 위에서 손실 복구, 스트림별 순서 관리, 흐름·혼잡 제어를 구현한다. 따라서 UDP를 쓴다는 사실만으로 응용 전체가 비신뢰적이라고 판단할 수 없다.

Q4. HTTP/2의 다중화와 QUIC의 차이는?

HTTP/2는 여러 스트림을 하나의 TCP 연결에 섞어 전송하지만 TCP 바이트 스트림의 손실은 여러 스트림을 지연시킬 수 있다. QUIC은 스트림별 순서 전달을 관리해 한 스트림의 손실이 다른 스트림의 전달까지 막는 문제를 줄인다.

Q5. 304 응답인데 왜 화면이 정상적으로 보이나?

클라이언트가 이미 가진 리소스를 조건부 요청으로 재검증했고 서버가 변경 없음을 알렸기 때문이다. 서버는 새 본문을 보내지 않고 클라이언트는 저장된 캐시 본문을 사용한다.

Q6. 서버 IP를 바꿨는데 일부 사용자만 옛 서버로 가는 이유는?

OS·브라우저·재귀 리졸버 등에 DNS 캐시가 남아 있을 수 있다. TTL이 만료되기 전까지 기존 주소가 사용될 수 있으므로 조회한 DNS 서버와 캐시 유효기간을 확인한다.

Q7. 스위치와 라우터의 차이를 주소와 함께 설명하라.

L2 스위치는 MAC 주소 테이블을 사용해 같은 링크 영역의 프레임을 전달한다. 라우터는 IP 주소와 라우팅 테이블을 바탕으로 서로 다른 네트워크 사이의 패킷을 전달한다.

Q8. TCP 종료가 4단계인 이유와 3개로 보일 수 있는 이유는?

양쪽 전송 방향을 각각 닫으므로 한쪽 FIN의 확인과 반대쪽 FIN이 필요하다. 일반적으로 FIN-ACK-FIN-ACK지만 상대의 종료 준비가 끝났다면 중간 ACK와 FIN을 하나로 합쳐 3개 세그먼트로 보낼 수 있다.

12. 시험 10분 전: 이것만 다시 보기

0~3분: TCP 표를 다시 그려라

C SYN 2000 → S SYN+ACK (3000,2001) → C ACK (2001,3001).

C DATA 200B (2001,3001) → S ACK (3001,2201) → S DATA 200B (3001,2201) → C ACK (2201,3201).

C FIN (2201,3201) → S FIN+ACK (3201,2202) → C ACK (2202,3202).

괄호는 SEQ, ACK 순서. SYN·FIN +1, 데이터 +길이, 순수 ACK +0. ACK는 “다음에 받을 번호”. 원본 예제는 종료 ACK와 FIN을 합친다.

3~5분: 비교 네 쌍

• 흐름 제어 = 수신자·rwnd. 혼잡 제어 = 네트워크·cwnd. 송신 제한 = min(rwnd,cwnd).

• TCP = 연결·바이트 스트림·순서·재전송·최소 20B. UDP = 비연결·데이터그램 경계·8B.

• L2 스위치 = MAC·프레임. 라우터 = IP·패킷. 포트 = 프로세스 통신 끝점.

• HTTP/2 = TCP 다중화. HTTP/3 = QUIC/UDP, TLS 1.3, 스트림 독립성, Connection ID.

5~7분: HTTP·DNS

200 성공 / 301·302 이동 / 304 캐시 재사용 / 401 인증 / 403 거부 / 404 없음 / 500 서버 오류.

Set-Cookie는 서버 → 브라우저. Cookie는 브라우저 → 서버. ETag → If-None-Match → 같으면 304.

DNS: 재귀 리졸버 → 루트 → TLD → 권한 DNS. A IPv4, AAAA IPv6, CNAME 별칭, MX 메일, NS 권한 서버. TTL은 캐시 유효기간.

7~9분: 계층·포트·진단

OSI 위→아래: 응용·표현·세션·전송·네트워크·데이터링크·물리.

80 HTTP, 443 HTTPS, 53 DNS, 25 SMTP, 587 제출, 110 POP3, 143 IMAP. HTTP/3는 보통 UDP 443.

ipconfig 설정 / ping 도달성·RTT / tracert 경로 / nslookup DNS / netstat 연결·PID / Test-NetConnection TCP 포트.

9~10분: 영상에서 추가한 숫자와 함정

Data Offset ×4 = TCP 헤더 B. 5→20B, 8→32B, 15→60B. /24는 255.255.255.0, 네트워크 부분으로 같은 망 판단. 손실 전까지 연속 수신한 다음 번호가 ACK다.

오답을 막아라

“UDP니까 오류 검출도 없다”, “DNS는 UDP만”, “ACK는 마지막 수신 번호”, “모든 ACK는 SEQ +1”, “HTTP/3는 무조건 더 빠름”, “304는 에러”, “ping 실패면 서버 다운”은 틀리다.

답안은 정의 → 동작 과정 → 차이 또는 이유의 순서로 쓴다. 계산에는 바이트 길이와 SYN/FIN 소비를 반드시 표시한다.

혼잡 윈도 그래프를 읽는 순서

전송계층4 04:26~12:19. 강의의 단순화된 라운드 그림: 시작 1 MSS → 2 → 4 → 8 → 16. 임계값에 도달하면 16 → 17 → 18처럼 선형으로 증가한다. 22에서 중복 ACK에 따른 감소는 약 절반인 11, 타임아웃이면 1에서 느린 시작을 다시 하는 그림이다.

시험에서는 문제에서 준 초기값·임계값·알고리즘을 우선한다. 실제 모든 TCP가 1 MSS에서 시작하거나 같은 폭으로 감소하는 것은 아니다. 고전적 혼잡 회피의 증가량은 대략 RTT당 1 MSS다. “ACK 하나마다 1 MSS씩 증가”와 혼동하지 않는다.

답안: 수신자 버퍼 한계는 rwnd, 망 혼잡은 cwnd로 제어한다. 느린 시작은 빠르게 용량을 탐색하고, 혼잡 회피는 완만히 증가시키며, 손실 신호가 있으면 송신량을 줄인다.

쿠키·세션·캐시를 한 흐름으로

쿠키캐시HTTPS 01:24~06:02: 서버가 Set-Cookie로 쿠키를 설정하면 브라우저가 이후 Cookie 헤더로 전달한다. 로그인 상태를 서버 세션과 세션 ID로 연결할 수 있다. 쿠키에 반드시 비밀번호를 저장하는 것은 아니다.

08:25~12:31: 브라우저 캐시는 이미 받은 자원을 재사용한다. CDN은 사용자 가까운 서버에서 자원을 제공해 먼 원본 서버까지 가는 지연과 트래픽을 줄인다.

12:42~14:29: ETag로 조건부 재검증. 같으면 304와 기존 본문 재사용, 바뀌면 새 본문을 포함한 200 응답. 304는 파일이 없다는 뜻이 아니다.

HTTPS와 QUIC

쿠키캐시HTTPS 16:34~17:56: 기밀성(도청 방지), 무결성(변조 검출), 인증(통신 상대 확인). 21:57~24:52: SNI는 접속하려는 서버 이름을 TLS 협상에 알리고, SAN은 인증서가 유효한 이름 목록을 담는다.

전송계층4 26:37~29:05: TCP는 순서가 맞아야 상위로 전달하므로 앞부분 손실이 뒤 전달을 막는다. HTTP/2 다중화만으로 TCP HOL이 없어지지는 않는다. QUIC은 스트림별 순서 전달로 다른 스트림에 미치는 영향을 줄인다.

29:15~30:47: Connection ID로 주소가 바뀌어도 연결을 이어갈 수 있다. UDP 자체가 비연결이라는 말과 QUIC도 연결이 없다는 말은 다르다. QUIC은 연결을 유지한다.

OSI 보충 영상의 비교 문제

OSI1 19:29~19:53: 데이터링크는 이웃 구간, 전송은 종단 사이의 역할. OSI2 22:43~23:40의 게이트웨이는 이종 프로토콜을 번역하는 넓은 의미다. PC 설정의 기본 게이트웨이(다른 망으로 보내는 라우터)와 문맥을 구분한다.

OSI2 27:06~27:28: 가정용 공유기는 라우터·NAT·스위치·무선 AP·DHCP 서버 등 여러 기능을 결합할 수 있다. “공유기는 OSI 한 계층 기능만 한다”라고 단정하지 않는다.
